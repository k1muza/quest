# Quest — Cinematic 2.5D Rendering Research and Development

## 1. Project context

Repository: https://github.com/k1muza/quest

Existing implementation:

`feature/unified-interactive-board`

Reference commit:

`6622636b30f7434392a275ba7bab9bfaf9490086`

The current Kingdom Quest implementation successfully combines a pre-rendered medieval environment with interactive playing pieces, automatic stopping positions, elevation-aware movement, per-pixel depth occlusion and a lightweight Canvas 2D presentation.

The current visual quality is provisionally rated 8.5/10.

However, the experience still feels more like an interactive board game illustration than a modern, immersive 3D game.

We would like to investigate how far the visual presentation can be improved while retaining the lightweight 2.5D runtime architecture.

## 2. Primary research objective

Investigate and demonstrate techniques for achieving the visual sophistication, depth, atmosphere and cinematic presentation of a modern 3D game without requiring real-time 3D rendering in the browser.

The eventual runtime target is a Smart TV browser.

Offline production may use Blender, Python, 3D geometry, physically based rendering and other computationally intensive techniques.

However, the delivered browser experience should continue to rely primarily on:

- HTML.
- CSS.
- JavaScript.
- Canvas 2D.
- Pre-rendered artwork.
- Transparent sprites.
- Depth maps.
- Image compositing.
- Lightweight procedural effects.

Do not introduce mandatory WebGL, Three.js, Unity or Unreal Engine runtime dependencies.

The objective is not merely to research theoretical possibilities.

**Produce actual visual experiments, working prototypes and a demonstrably improved standalone experience wherever technically feasible.**

Investigate the appropriate production resolution for smooth cinematic zooming.

- 1920 × 1080.
- 2560 × 1440.

- 7680 × 4320, where practical.

Compare:

Evaluate suitable image formats, including JPEG, WebP, PNG and other formats where browser compatibility permits.

Measure the actual trade-offs.

The selected approach should allow convincing close-up views without requiring an unnecessarily large runtime memory footprint.

## 8. Experiment D — Cinematic camera system

Develop a working camera prototype.

The current implementation supports basic pan and zoom. Investigate how this can become a polished cinematic presentation system.

### Overview camera

Maintain a complete view of the map and all competing teams.

This should remain the normal spectator view.

### Active-team camera

Smoothly approach the active team's location during significant events.

The camera may follow the team's playing piece during movement.

### Landmark camera

Create carefully composed close-up views of important locations, including:

- Starting village.
- Agricultural district.
- Dense forest.
- River crossing.
- Mountain pass.
- Developed township.
- Royal gate.
- Royal courtyard.

### Victory camera

Investigate a dramatic camera sequence highlighting the winning team or the royal citadel during final results.

The winner must remain visually associated with their actual authoritative position.

Do not imply that a team has reached the castle if it has not.

### Camera behaviour

Implement or prototype:

- Smooth interpolation.
- Cinematic easing.
- Controlled zoom.
- Automatic framing.
- Camera following.
- Safe viewport boundaries.
- Return-to-overview transitions.
- Interruption handling when new game events arrive.

Avoid excessive camera movement during ordinary scoring.

Investigate the best occasions for cinematic transitions, such as:

- Turn handover.
- Significant scoring events.
- Landmark crossings.
- Turn completion.
- Final results.

Produce an interactive demonstration allowing each camera mode to be evaluated.

## 9. Experiment E — Independently rendered cinematic viewpoints

- A dramatic view across the river bridge.
- A view looking through the mountain pass.
- A street-level or elevated township view.
- A ceremonial approach to the castle.

Each alternative camera should have its own:

- Background artwork.
- Camera projection.
- Depth information.
- Route projection.
- Playing-piece scale.
- Foreground occlusion data.
- Relevant environmental animation anchors.

The same authoritative world coordinates must be projected correctly into each camera.

Do not manually approximate token positions on alternative images.

Evaluate whether transitions between cameras should use:

- Direct cinematic cuts.
- Crossfades.
- Fade-through transitions.
- Pre-rendered transition sequences.

Do not attempt arbitrary continuous camera rotation using a single static background.

Do not introduce technically inaccurate perspective interpolation between unrelated camera images.

Produce at least two working landmark viewpoints with correctly positioned interactive playing pieces if feasible.

Prioritise the bridge crossing and royal citadel as initial experiments.

## 10. Experiment F — Depth-aware atmospheric effects

The current implementation already exports per-pixel scene depth and pawn depth.

Investigate how this information can be reused to improve visual depth.

Potential applications include:

- Depth-dependent fog.
- Atmospheric perspective.
- Selective background softening.
- Subtle depth-of-field effects.
- Foreground particles.
- Ground-level mist.
- Depth-aware sunlight effects.
- Localised lighting.
- More convincing environmental occlusion.

Where practical, render these effects offline or use efficient precomputed masks.

Avoid full-screen per-pixel processing every frame if it creates excessive CPU overhead.

Test whether cached layers or low-resolution effect buffers provide acceptable results.

Ensure that atmospheric effects do not obscure team pieces, road markers or essential spectator information.

## 11. Experiment G — Parallax and layered environments

Investigate whether restrained parallax can improve the illusion of depth during camera movement.

Potential independently rendered layers include:

- Distant terrain.
- Mountains.
- Water.
- Buildings.
- Foreground trees.
- Clouds.
- Mist.

Determine whether the existing geometry can be rendered into transparent, depth-separated layers.

Consider the need for background completion where moving layers reveal previously hidden areas.

Preserve the spatial alignment of:

- Roads.
- Terrain.
- Stopping markers.
- Playing pieces.
- Depth masks.

Do not introduce parallax that makes buildings or vegetation slide unnaturally across the ground.

A technically convincing subtle effect is preferable to an exaggerated effect that breaks the world's visual integrity.

Produce a prototype only if the technique can preserve spatial correctness.

## 12. Experiment H — A living environment

Prioritise:

### River and coastal water

- Directional river flow.
- Animated water highlights.
- Gentle waves.
- Shoreline foam.
- Reflections.

### Windmills

Separate rotating blades from static structures.

Ensure that rotation remains aligned with the rendered building perspective.

### Flags and banners

### Chimney smoke

Introduce subtle, intermittent smoke from selected buildings.

### Boats

Investigate gentle rocking or movement near harbour areas.

### Wildlife

Consider occasional birds or other restrained environmental activity.

### Clouds

Investigate slow-moving cloud shadows or atmospheric cloud layers.

Avoid duplicated windmill blades, static flags behind animated flags or overlapping shadows.

Evaluate the visual improvement and runtime cost of each effect.

Produce working demonstrations of the most promising effects.

## 16. Performance investigation

The current standalone implementation reports:

- Approximately 1.98 MB runtime size.
- Approximately 60 FPS in headless Chromium.
- Approximately 162 ms initial asset decoding.
- Approximately 31 MB JavaScript heap usage.

Treat these figures as the baseline reported by the previous implementation, not independently verified Smart TV benchmarks.

Measure the impact of each proposed enhancement on:

- Runtime distribution size.
- Asset decoding.
- Initial loading.
- Peak decoded image memory.
- JavaScript heap usage.
- Canvas memory.
- Frame cadence.
- Animation responsiveness.
- Camera transition performance.

Test with:

- 1280 × 720.
- 1920 × 1080.
- 3840 × 2160 where practical.
- Two teams.
- Six teams.
- Multiple simultaneous animations.
- Rapid score updates.

Investigate appropriate quality profiles.

### Standard profile

Preserve lightweight operation on modest television browsers.

### Enhanced profile

Enable improved artwork, selected environmental animations and cinematic zoom.

### Cinematic profile

Enable higher-resolution assets, alternative camera viewpoints and additional effects where hardware permits.

The underlying gameplay functionality must remain consistent across profiles.

Investigate adaptive quality selection if it is practical and reliable.

Do not claim actual Smart TV compatibility unless physical hardware has been tested.

## 18. Investigation methodology

Conduct this work experimentally.

For each significant technique:

1. Explain the hypothesis.
2. Implement the smallest meaningful prototype.
3. Produce an actual rendered output.
4. Compare it against the baseline.
5. Measure the runtime or production cost.
6. Identify technical limitations.
7. Decide whether to adopt, refine or reject the technique.

Do not merely enumerate theoretical possibilities.

If a technique is unsuccessful, preserve the useful findings and explain why it was rejected.

Prioritise actual implementation over speculative architectural documentation.

Where an experiment encounters a blocker, investigate reasonable alternative approaches and continue with the remaining experiments.

Do not allow one unavailable dependency or rendering tool to prevent useful progress elsewhere.
